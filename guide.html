Bazarr sits off to the side, watching the finished library and fetching subtitles. FlareSolverr sits behind Prowlarr, solving Cloudflare challenges on indexers that use them. Gluetun wraps qBittorrent alone — it's the only container whose traffic leaves through NordVPN, so streaming and the web UIs stay on your LAN at full speed.

Music runs as a parallel lane with the same bones: Lidarr is Sonarr/Radarr for albums, Navidrome streams them, and Mixarr is the discovery layer that feeds Lidarr from Spotify, TIDAL, Last.fm and the rest. Everything reuses Prowlarr and the qBittorrent + gluetun tunnel already in the stack.

The one idea that matters

Downloads and the library live on the same filesystem, under one bind mount. That lets Sonarr and Radarr hardlink a finished download into the library instead of copying it: instant, and it costs zero extra disk while the torrent keeps seeding. Almost every "why is my disk full" and "why does importing take 20 minutes" post traces back to breaking this rule.

01

Give the disk a permanent mount

Right now the drive lands at /media/<user>/<LABEL>, mounted by your desktop session when you log in. That path is wrong for Docker on two counts: it contains a space, and it does not exist until a graphical login happens.

Why this is step one

If Docker starts before that mount appears, every container happily creates its folders at the empty path and writes to your 128 GB system SSD instead. You find out when the root filesystem fills and the whole machine falls over. An /etc/fstab entry mounts the disk at boot, long before Docker.

The drive is internal SATA (a Seagate ST2000LM007), so a permanent mount is simply correct — nothing here is hot-swapped.

Run the prep script

terminal · needs sudo
lsblk -f   # copy the UUID of the library disk (e.g. /dev/sdb2)
sudo DISK_UUID=<disk-uuid> MOUNT_POINT=/mnt/disco bash ~/media-stack/setup-host.sh

It backs up /etc/fstab first, then writes this line:

/etc/fstab
UUID=<disk-uuid>  /mnt/disco  ntfs3  defaults,nofail,noatime,uid=1000,gid=1000,umask=002,windows_names,x-systemd.device-timeout=10  0  0
OptionWhat it buys you
UUID=…Survives the disk being redetected as sdc after a reboot.
nofailA missing disk doesn't drop the whole boot into emergency mode.
uid=1000,gid=1000NTFS has no Unix permissions, so they're synthesised at mount time. Matches PUID/PGID in the stack.
umask=002Directories 775, files 664 — group-writable, so every container can import.
windows_namesRejects filenames NTFS can't represent, so you fail loudly at creation instead of getting silent corruption later.
noatimeNo pointless write on every read. Meaningful on a spinning 5400 rpm drive.
The immutable-mountpoint trick

The script runs chattr +i /mnt/disco on the empty directory before mounting. While the disk is mounted this does nothing. If the disk ever fails to mount, the bare directory underneath is read-only and containers error out immediately — loud failure instead of quietly filling your SSD. Keep it.

Verify before going further

terminal
findmnt /mnt/disco
df -h /mnt/disco

You want to see /dev/sdb2 and roughly 1.2T available. If you don't, stop here — nothing downstream will work.

Side effect

The drive stops appearing in your file manager's sidebar and lives at /mnt/disco. Any desktop bookmark pointing at the old /media/… path breaks.

02

Folder layout

The script creates this. It is not arbitrary — the shape is what makes hardlinks possible.

on the library disk
/mnt/disco/data/
├── torrents/          # qBittorrent writes here, keeps seeding here
│   ├── movies/
│   ├── tv/
│   └── music/
└── media/             # Jellyfin / Navidrome read here
    ├── movies/
    ├── tv/
    └── music/

Every container that touches files mounts the single parent /mnt/disco/data as /data. Both subtrees are therefore one filesystem as the container sees it, and hardlinking works.

Do not do this

Mounting …/torrents:/downloads and …/media:/media as two separate binds is the classic mistake. Docker presents them as different devices, so Sonarr falls back to a full byte-for-byte copy — slow, and it doubles your disk usage for every file you seed.

Config databases go on the SSD at /opt/appdata/…, deliberately not on the NTFS disk. SQLite needs POSIX locking that NTFS doesn't provide properly; putting the .db files there corrupts them eventually.

I already confirmed hardlinks work on your NTFS volume, so the layout is sound as-is.

03

Deploy the stack in Portainer

  1. Portainer → Stacks → Add stack.
  2. Name it media.
  3. Build method Web editor, and paste the contents of ~/media-stack/docker-compose.yml.
  4. Under Environment variables, set the host details the compose interpolates: SERVER_IP (this machine's LAN IP), LAN_SUBNET (e.g. 192.0.2.0/24) and DATA_DIR (e.g. /mnt/disco/data). Deploying with docker compose from a terminal instead? Copy .env.example to .env and fill it in there — Portainer ignores .env.
  5. Scroll to Environment variables → Add an environment variable and set WIREGUARD_PRIVATE_KEY to your NordLynx key (cat ~/media-stack/nordlynx.key). The stack will refuse to deploy without it — that's deliberate, so you can never accidentally run the torrent client outside the tunnel.
  6. Add a second variable, SESSION_SECRET — a long random string that Mixarr uses to encrypt sessions. Generate one with openssl rand -hex 32 and paste it. It only matters for Mixarr; everything else ignores it.
  7. Deploy the stack. First pull is a few GB — Jellyfin is the big one.
Deploy order is handled for you

qBittorrent has depends_on: gluetun (service_healthy), so it won't start until the tunnel is actually up and passing gluetun's own health check. There is no window where it could leak traffic while the VPN is still connecting.

Port 8080 was already taken

Your Nextcloud container holds 8080, so qBittorrent's web UI is on 8085 instead — set in both the WEBUI_PORT variable and the published port. Changing one without the other gives you a container that starts but never answers.

All twelve containers share a network called media, which is why they can reach each other by container name — http://sonarr:8989 and so on. Never use localhost between containers; inside a container that means the container itself.

terminal · confirm all twelve are up
# Filtra por proyecto, no por red: qbittorrent no está en la red 'media',
# vive dentro de la pila de red de gluetun.
docker ps --filter label=com.docker.compose.project=media \
          --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
Expected

Twelve containers, all Up, with gluetun showing (healthy). qBittorrent will list no ports of its own — correct, they belong to gluetun. Anything stuck in Restarting, read its log with docker logs <name> before continuing.

The host is gluetun, not qbittorrent

This trips up everyone. qBittorrent runs inside gluetun's network stack, so it has no network identity of its own — Docker's DNS has no record called qbittorrent at all. Music stack — Lidarr · Navidrome · Mixarr

Music is a parallel lane on the same plumbing. Lidarr downloads and imports albums into /data/media/music, Navidrome streams that folder, and Mixarr finds new artists to feed Lidarr. Prowlarr, qBittorrent and gluetun are all shared with the video stack.

a · Lidarr — 8686

Open http://192.0.2.10:8686 and set the admin credentials. Then:

  1. Settings → Media Management (advanced settings on): Rename albums on, Replace Illegal Characters on, Use Hardlinks instead of Copy on.
  2. Settings → Media Management → Root Folder: /data/media/music.
  3. Settings → Download Clients → Add → qBittorrent: Host gluetun, port 8085, your credentials, category lidarr. Test — green tick or stop.
  4. Settings → General → API Key: copy it, then add Lidarr in Prowlarr (Settings → Apps) exactly like Sonarr/Radarr with http://lidarr:8686. Indexers sync over automatically.
  5. Create the category in qBittorrent first (lidarr → /data/torrents/music), matching what you typed in step 3.
Expect missing metadata on obscure albums

MusicBrainz is the metadata source and its cache gets hammered; some niche albums land with no artwork or wrong tags. Lidarr's Tasks → Refresh Artist is the retry button. Also, the good music torrent indexers are mostly private (Redacted, Orpheus) — public ones are thin, so expect fewer grabs than with video.

b · Navidrome — 4533

Open http://192.0.2.10:4533 and create the admin account on first run. It scans /data/media/music automatically every hour — point it at the library if it asks, and it will show whatever Lidarr has imported. Use Finamp (iOS/Android) or Symfonium on the phone for playback.

c · Mixarr — 3443 (HTTPS)

Open https://192.0.2.10:3443 (self-signed cert — accept the warning) and create the admin account. Then:

  1. Settings → Global: Base URL already set to https://192.0.2.10:3443 — leave it.
  2. Settings → Connections → Lidarr: http://lidarr:8686 + API key.
  3. Settings → Services: connect Last.fm, ListenBrainz, TIDAL or Deezer (OAuth). This is what powers discovery. Spotify no longer works on a free account — see the note below.
  4. Create subscriptions under Discover → Subscriptions (e.g. a Spotify playlist, Last.fm tag, or global charts). New finds land in the Review queue for approval before Lidarr ever sees them.
How it reaches Lidarr

Mixarr talks to Lidarr over the media network by name. It never touches your files — it only asks Lidarr to add approved artists, and Lidarr does the grabbing via the same qBittorrent tunnel as everything else.

Why Spotify is not on that list

Since February 2026 Spotify requires the developer account that owns the app to hold an active Premium subscription — Development Mode apps on a free account are blocked from the Web API entirely. Every call returns 403 Forbidden, and no amount of allowlisting fixes it. The same round of changes cut authorized users per app from 25 to 5 and limits you to one Client ID. Last.fm and ListenBrainz need only a free API key, so use those instead.

d · ytm-bridge — 8099

YouTube Music has no official API and Lidarr has no YTM import list, so this small service bridges the gap: it reads your YTM recommendations, resolves the artist names to MusicBrainz IDs, and publishes them as a JSON list Lidarr can subscribe to.

  1. Get YTM credentials. On your desktop, open https://music.youtube.com logged in, press Ctrl-Shift-I → Network tab, filter by /browse, click any POST request, open Request Headers and switch it to the Raw view. Copy all of it into a text file, then run ./ytm-bridge/make-auth.sh ~/ytm-headers.txt. That writes /opt/appdata/ytm-bridge/headers_auth.json. Credentials stay valid ~2 years unless you log out.
  2. Doing it by hand instead? pipx run ytmusicapi browser --file headers_auth.json works too, but it reads until end-of-input — after pasting you must press Ctrl-D or it just sits there. It also prints the JSON to stderr and exits 1 even on success; check whether the file exists rather than trusting the exit code. The wrapper script handles both. The bridge accepts headers_auth.json, the default browser.json, or an oauth.json.
  3. Export the API key. Lidarr → Settings → General → API Key, then export LIDARR_API_KEY=… alongside the other secrets before docker compose up -d.
  4. Bootstrap with Takeout (optional). Google Takeout → YouTube and YouTube Music → your library as CSV. Unzip the CSVs into /opt/appdata/ytm-bridge/takeout/ and the bridge folds years of listening into the list on the next refresh. Any column whose header mentions artist is picked up, so format changes on Google's side don't break it.
  5. Point Lidarr at it. Lidarr → Settings → Import Lists → + → Custom List (under Advanced). List URL: http://ytm-bridge:8080/artists.json. Set Monitor, Quality Profile, Metadata Profile and Root Folder (/data/media/music) as you like, then Test and Save.

Check http://192.0.2.10:8099/status to see the last refresh, how many artists were published, and which names it could not resolve. curl -X POST http://192.0.2.10:8099/refresh forces a run instead of waiting for the 12-hour cycle.

Leave Search on New Items off at first

The first refresh can publish hundreds of artists. If Lidarr is set to search immediately, that is hundreds of simultaneous indexer searches — a fast way to get rate-limited or banned. Import once with searching disabled, prune what you do not want, then turn it on.

Why not just yt-dlp the music

You could pull the audio straight off YouTube, but it tops out around Opus 256kbps with scraped tags, which fights both Lidarr's release matching and Navidrome's organization. Using YTM for discovery and your existing indexers for acquisition keeps one clean, properly tagged library. Keep yt-dlp for the rare thing no indexer has.

e · In qBittorrent

Add the lidarr category (/data/torrents/music) if Lidarr's test didn't already force it. Seeding limits: albums seed on ratio like anything else.

Prove the whole chain works

One request, end to end. Pick something small and well-seeded.

  1. In Jellyseerr, search a film and hit Request.
  2. Radarr Activity → Queue shows it grabbed within a minute or so.
  3. qBittorrent shows it downloading under the radarr category.
  4. On completion, Radarr imports it and it appears under /data/media/movies.
  5. Jellyfin picks it up on the next scan — force one from Dashboard → Libraries → Scan.
  6. Play it.

Confirm the hardlink actually happened

This is the test worth running once, because a silent fallback to copying is invisible until the disk is full:

terminal
# Link count of 2 means one file, two names — the hardlink worked.
find /mnt/disco/data/media -type f -links +1 -printf '%n  %p\n' | head

# And the space check: used should be far less than the sum of both trees.
du -sh /mnt/disco/data/torrents /mnt/disco/data/media
df -h /mnt/disco
Reading the result

If du reports, say, 40 G + 40 G but df shows only 40 G consumed, hardlinks are working exactly as intended. If the disk really lost 80 G, Radarr copied instead — go back and check Use Hardlinks instead of Copy and that both containers mount the single /data parent.

When it breaks

Every container fails at once, disk reads read-only

This is the NTFS one, and it will happen eventually — an unclean shutdown sets the dirty bit and ntfs3 refuses to mount read-write.

terminal · the NTFS fix
P=label=com.docker.compose.project=media
docker stop $(docker ps -q --filter $P)
sudo umount /mnt/disco
sudo ntfsfix -d /dev/sdb2
sudo mount /mnt/disco
docker start $(docker ps -aq --filter $P)
The long-term answer

NTFS is the one genuinely fragile part of this build. ext4 removes this whole failure class, but converting means relocating the 708 GB already on the drive. Not worth doing today — worth doing the next time you have a spare disk to stage through.

Routine maintenance

  • Watch free space. Seeding plus a 1080p habit fills 1.2 TB faster than you'd guess. Set seeding limits in qBittorrent so completed torrents eventually clear.
  • Back up /opt/appdata. That's every setting, request history and library database in the stack. You have Nextcloud right there.
  • Update deliberately. In Portainer, Recreate with "pull latest image" — one container at a time, not all eight at once, so you know what broke.

How the VPN is wired

Gluetun is part of the stack, not an optional extra. Only qBittorrent routes through it; Jellyfin, Jellyseerr and the rest stay on the LAN at their normal addresses. Reference material — nothing to do here beyond understanding it.

Getting your NordLynx key

Nord never displays the WireGuard private key. You generate an access token at nordaccount.com → Services → NordVPN → Manual setup → Generate new token, then trade it for the key:

terminal
~/media-stack/get-nordlynx-key.sh

The key lands in nordlynx.key with 600 permissions — 44 characters ending in =. It goes into Portainer's environment variables as WIREGUARD_PRIVATE_KEY, never into the compose text itself.

Don't read it off the local client

wg show nordlynx private-key is the usual shortcut, but you have Meshnet enabled — which holds the same nordlynx interface with a different key. You'd get the Meshnet key and gluetun would never complete a handshake.

NordVPN has no port forwarding

Nord dropped it entirely, and gluetun can only negotiate forwarded ports with providers that offer it (PIA, ProtonVPN). So there's no point publishing 6881 on the host any more, and it isn't in the compose. Practically: qBittorrent can still connect out to peers and downloads work fine, but no peer can initiate a connection to you. Expect slower starts on thinly-seeded content, and be aware that private trackers which measure connectability will mark you unconnectable. If you ever join one, that's the moment to reconsider the provider — not the setup.

Why not just run the NordVPN client

nordvpn connect routes the entire machine — Jellyfin, Nextcloud, Sunshine, all of it — through the tunnel, which breaks LAN access for everyone in the house and would kill your Moonlight streaming. Keep the desktop client disconnected. Meshnet can stay on; it doesn't conflict with gluetun, which builds its own tunnel inside the container.
